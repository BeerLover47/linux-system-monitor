## 🏛 Архитектурные стандарты (Chapter III)

1. **Модульность:** Сценарии не пишутся монолитными простынями. Вся логика разбита на подключаемые модули:
   ```
   01/
   ├── main.sh       # Точка входа (валидация $#, импорт, координация)
   ├── validate.sh   # Проверка типов параметров и граничных условий
   ├── generator.sh  # Алгоритмы конструирования имён
   └── create.sh     # Работа с диском, fallocate, контроль свободного места
   ```
2. **Безопасное подключение модулей:** Независимость от директории вызова через `${BASH_SOURCE[0]}`:
   ```bash
   DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
   source "$DIR/validate.sh"
   ```
3. **Безопасность диска:** Мониторинг свободного места через `df --output=avail -m /` с аварийной остановкой при остатке $\le 1024$ Мб во избежание сбоя хостовой ОС.

#### 🖥 Способ 1: Прямо в терминале (TUI) — САМЫЙ БЫСТРЫЙ И НАГЛЯДНЫЙ НА ПРОВЕРКЕ

**Как показать пиру ответы на 4 пункта задания прямо в консоли:**
1. **Коды ответов:** Нажми цифру `8` (панель *HTTP Status Codes*) $\to$ `Enter`.  
   👉 *Покажи пиру:* «Вот все коды (200, 400, 404, 500), число запросов и проценты». Нажми `q`.
2. **Уникальные IP:** Нажми цифру `3` (панель *Visitor Hostnames and IPs*) $\to$ `Enter`.  
   👉 *Покажи пиру:* «Вот список всех уникальных IP-адресов посетителей и объем переданного трафика». Нажми `q`.
3. **Запросы с ошибками (4xx и 5xx):** Снова нажми `8` (*HTTP Status Codes*) $\to$ `Enter`.  
   👉 *Покажи пиру:* «Секции 4xx Client Errors и 5xx Server Errors суммируют все ошибки. А в панели 4 (Not Found URLs) детализированы битые пути 404». Нажми `q`.
4. **Уникальные IP ТОЛЬКО среди ошибок (Главный козырь!):**  
   Выйди из GoAccess (`q`) и запусти конвейер:
   ```bash
   awk '$9 ~ /^[45]/' 04/*.log | goaccess - --log-format=COMBINED
   ```
   Нажми цифру `3` (*Visitor Hostnames and IPs*) $\to$ `Enter`.  
   👉 *Покажи пиру:* «В GoAccess таблицы IP и статусов разделены. Поэтому мы потоково отфильтровали логи через awk (оставив только 4xx/5xx) и передали в GoAccess через stdin (`-`). Теперь в списке уникальных IP находятся **исключительно IP с ошибками**!».

```bash
# Синтаксис: main.sh (без аргументов)
bash 07/main.sh
```
Запускает интерактивное меню управления тестами (`07/menu.sh`).

#### 📊 Где смотреть метрики:
* **Grafana:** `http://192.168.56.101:3000` (логин: `admin`, пароль: `admin`).
* **Prometheus:** `http://192.168.56.101:9090`.
* Кастомный дашборд содержит 4 обязательные панели:
  1. **CPU Usage:** `100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[$__rate_interval])) * 100)`
  2. **Available Memory:** `node_memory_MemAvailable_bytes`
  3. **Free Disk Space:** `node_filesystem_avail_bytes{mountpoint="/"}`
  4. **Disk I/O:** `sum by (instance) (rate(node_disk_reads_completed_total[1m]))` / `sum by (instance) (rate(node_disk_writes_completed_total[1m]))`

#### 🎯 Пошаговый сценарий демонстрации пиру:
1. **Тест CPU и памяти:** В меню нажми `1` (запуск `stress`).  
   👉 В Grafana покажи: пик загрузки на панели **CPU** (до 100%) и расход памяти **Available Memory**.
2. **Тест диска:** В меню нажми `2` (запуск `02/main.sh`).  
   👉 В Grafana покажи: падение свободного места на панели **Free Disk Space** и резкий всплеск графика **Disk I/O** (запись на диск).
3. **Очистка диска:** В меню нажми `3` (запуск `03/main.sh`, выбери любой режим, например `1` или `2`).  
   👉 В Grafana покажи: график свободного места вернулся в исходное состояние.

> 💡 **Вопрос пира:** *«Почему для CPU формула `100 - idle`?»*  
> **Ответ:** Метрика `node_cpu_seconds_total` считает время работы процессора в секундах. Режим `mode="idle"` — это время простоя (безделья). Функция `rate` считает долю простоя от 0 до 1. Если процессор простаивает 20% времени, значит загружен на $100\% - 20\% = 80\%$. Поэтому формула: `100 - (idle * 100)`.

#### ⚠️ ВАЖНО: Как правильно проводить сетевой тест iperf3 (НЕ PING!):
> `ping` **НЕ подходит для проверки нагрузки**, так как он шлёт маленькие служебные пакеты по 64 байта и не нагружает сеть (трафик в Grafana останется около 0).  
> `iperf3` генерирует поток данных в сотни мегабит/с между двумя машинами (Клиент $\leftrightarrow$ Сервер).

#### 🚀 Пошаговый запуск iperf3 для проверки:

**Вариант А (Самый простой и надёжный — сервер на ВМ, клиент с хоста/WSL):**
1. **На твоей ВМ (где крутится Grafana и Node Exporter):**  
   Открой отдельную вкладку терминала и запусти сервер `iperf3`:
   ```bash
   iperf3 -s
   ```
   *(Терминал напишет: `Server listening on 5201` — сервер ждет входящий трафик)*.

2. **На основной машине (в WSL, PowerShell или на 2-й ВМ):**  
   Запусти клиента, указав IP виртуальной машины:
   ```bash
   iperf3 -c 192.168.56.101 -t 30 -P 4
   ```
   *(Клиент начнет перекачивать данные в 4 параллельных потока в течение 30 секунд)*.

3. **Что показывать пиру в Grafana:**
   - Открой дашборд **13978** (*Node Exporter Quickstart*).
   - В правом верхнем углу поставь интервал **Last 5 minutes** и обновление **5s**.
   - Найди панель **Network Traffic** (график **Network Received**).
   - 👉 *Покажи пиру:* **«Вот всплеск графика с 0 до 500+ Мбит/с — это сетевая карта ВМ принимает трафик от iperf3!»**.

1. В WSL/на хосте запусти: `iperf3 -s`.

3. **Два главных вопроса пира по коду Part 9:**
   - **Вопрос 1:** *«Почему тип `gauge`, а не `counter`?»*  
     👉 **Ответ:** `Counter` может только расти (как пробег автомобиля). А CPU, свободная память и свободный диск могут как увеличиваться, так и уменьшаться — это шкала (`gauge`).
   - **Вопрос 2:** *«Зачем мы сначала пишем в `.tmp`, а потом делаем `mv` в `metrics.html`?»*  
     👉 **Ответ:** Для **атомарности**. Команда `mv` вызывает системный вызов ядра Linux `rename(2)`. Если бы мы писали сразу `> metrics.html`, файл на 50 мс обнулялся бы при перезаписи, и Prometheus скрейпил бы пустой файл (ошибка сбора). С `mv` файл подменяется мгновенно!
